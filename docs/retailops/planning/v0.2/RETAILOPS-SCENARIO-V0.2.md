# RetailOps Agent：单店商超智能经营决策场景扩展说明

版本：V0.2（候选业务定位，待确认）

## 1. 项目定位

基于 OpenDot 的单店商超经营决策 Agent，服务一家同时具备实体门店、线上下单和即时配送能力的中小型超市，以生鲜商品为切入点，解决经营异常诊断、库存补货、动态定价和损耗治理问题。Agent 按店长设定的目标自主选择查询、预测、测算工具，形成有证据的经营建议，经独立风控和人工审批后在仿真业务系统中执行，并追踪效果。项目不替代 POS、商城或 ERP，不重新开发通用 Agent 框架。

## 2. 场景边界

- 一家门店，一个共享库存，线下 POS 与线上订单作为两个销售渠道；线上订单区分预占、完成、取消，避免重复扣库。
- 建议初期选择 20–50 个生鲜 SKU，少量模拟供应商；第一条验收链路仅使用一个商品、一个临期批次。
- 店长负责审批，经营分析 Agent 提出方案；独立只读风控角色审查；受控服务执行。
- 初期使用本地历史回放及有种子的经营仿真，不连接真实收银、支付、采购或称重硬件。
- 不做跨门店调拨、区域仓、完整商城、物流配送、消费者推荐、复杂大促、多供应商自动采购谈判。选品与视觉称重异常仅作为后续可选场景。

### 真实数据边界

叮咚买菜公开数据集 [FreshRetailNet-50K](https://huggingface.co/datasets/Dingdong-Inc/FreshRetailNet-50K)（[论文](https://arxiv.org/abs/2505.16319)，CC BY 4.0）提供约 50,000 条门店商品时间序列，覆盖 898 家门店、865 个生鲜 SKU，单条序列 90 天。选择一个具备足够商品覆盖的 store_id，保留原始 product_id 与日期，提取 sale_amount、hours_sale、hours_stock_status、stock_hour6_22_cnt、discount、holiday_flag、activity_flag、avg_temperature 等字段。

公开销量经过全局归一化，不能直接当作实际件数、公斤数或金额；缺货标记不等于库存数量。数据不含完整 POS 流水、渠道拆分、库存批次、采购成本或供应商。需求预测在原始归一化尺度评价；仿真交易使用另行定义的商品单位、成本、售价、库存、批次及价格响应，明确映射假设。不得把仿真经济结果当作真实生产收益。

数据分层：PUBLIC_HISTORICAL（公开历史）、SIMULATED（仿真）、DERIVED（派生，保留上游来源）、LIVE_DEVICE（未来可选，当前不存在）。数据清单记录源 URL、许可、版本、筛选条件、哈希、时间、单位与生成种子；原始数据只读。公开数据署名，不将不必要的大型原始文件直接提交 Git。

## 4. 三项核心业务

| 能力 | 业务动作 | 边界 |
|---|---|---|
| 异常诊断 | 识别销售异常、缺货与库存积压，调查活动、天气、库存状态等证据 | 规则触发，Agent 选择调查路径；相关性不等于因果 |
| 生鲜损耗与动态定价 | 对仍可销售的临期批次比较原价、折扣、暂缓补货等方案 | 过期或质量异常商品不得销售；折扣须审批，不直接写 POS |
| 智能补货 | 预测需求，考虑可售库存、预占、在途及到货周期，计算建议补货量 | 生成模拟采购草案，审批后模拟执行，不向真实供应商下单 |

第一条纵向切片：单 SKU 临期库存积压 → 异常识别 → 动态查询证据 → 需求预测 → 原价与折扣比较 → 规则审查 → 店长审批 → 仿真调价 → 下一经营周期评价。第二条切片才加入补货及双渠道库存。销售趋势预测与仿真价格响应不混淆。

## 5. 业务示例（全部为仿真参数）

下午店长发现某一批仍可销售的水果库存 100 盒，单位成本 8 元，原售价 15 元，剩余窗口预计原价销售 40 盒。Agent 查询批次、销售和促销政策，计算不同价格方案。若仿真假设八折可售 70 盒，则原价收入 600 元、折扣收入 840 元；若窗口结束未售商品无残值且整批采购成本 800 元，忽略其他费用时，整批简化经营贡献分别为 -200 元、40 元。折扣需求 70 盒是仿真假设，不是从公开数据得出的因果结论；没有可信估计时，应输出情景区间或拒绝推荐。真实质量与食品安全限制不可由模型或审批绕过。

## 6. OpenDot 集成候选

| 底座能力 | RetailOps 用途 |
|---|---|
| Host / Pi Runtime | 经营分析 Agent 的真实多步工具调用 |
| Tool / MCP | 销售、库存、批次、政策、预测与方案测算工具 |
| Goal / Scheduler | 后续定时监测与经营复盘 |
| Durable | 审批暂停、异常恢复及长任务状态 |
| Handoff | 独立分析与风控审查 |
| Approval | 冻结业务草案、绑定参数摘要与授权身份 |
| Context / Memory | 调查上下文与历史经验；权威经营政策独立版本化 |
| Trace / Eval | 证据链、决策质量及执行结果 |

OpenDot 已有运行报告确认 Host / local-pi、DeepSeek 模型、多步 Tool Calling 和刷新后历史持久化。Product Durable、Product MCP 审批、Goal 与 Handoff 等关键路径尚不能据此判定为真实运行通过，须继续 RETAIL-00B 调查验证。业务状态与通用 Goal 状态分别管理；现有私有产物审批不是调价审批，MCP 审批的集成边界待验证。保留 TypeScript、SQLite、现有 Web 和身份授权，不先引入其他通用 Agent 框架。

候选工具：query_sales、query_inventory_lots、query_stockout_history、query_retail_policy、forecast_demand、compare_markdown_options、calculate_replenishment、submit_decision_draft。只读工具显式授权；写动作经独立执行服务和人工审批，默认拒绝未知工具。执行前核对草案版本、完整参数摘要、政策版本、权限、库存与数据时效。执行幂等键和可查询回执独立持久化，结果未知时冻结并对账，不盲目重试。

## 7. Eval 与验收

- 预测：以时间顺序拆分训练与评估，比较同星期均值等基线，记录 MAE/WAPE、缺货区间误差及数据限制；不得使用未来信息。
- 仿真：固定随机种子、初始库存、需求场景及价格响应参数，比较固定规则策略、Agent 策略；记录利润口径、损耗率、缺货率、需求满足率。结果仅代表仿真。
- Agent：工具调用正确性、证据覆盖率、无依据结论、硬规则违规、审批绕过、重复执行、失败与恢复行为。
- 至少覆盖正常调价、过期商品拒绝、库存变化导致草案失效、审批拒绝/重复、执行结果未知、服务重启恢复；分开记录 fixture、真实模型、真实运行时测试。

## 8. 开发顺序

1. 保留已归档的 RETAIL-00A 基线，继续 RETAIL-00B 深度源码调查与关键功能验证。
2. 通过 RETAIL-00C 确认场景边界、数据口径、领域 Schema、权限和架构 V0.2；视需要并行执行开源领域调查。
3. V0：单 SKU 临期折扣闭环（先确定性规则与仿真，再接真实 Agent、风控、审批和 UI）。
4. V1：扩展至少量 SKU、需求预测、缺货诊断与补货，加入双渠道共享库存。
5. V2：定时经营、Durable 恢复、Trace/Eval 与必要的仿真称重事件；可选视觉设备接入另行评估。

本文是场景设计草案，不是已实现功能说明。尚未下载处理数据、运行第三方案例、核实全部代码许可证或完成高级 Runtime 验证。具体库存及损耗口径、价格响应、供应商规则与阈值需在后续 Issue 确认。原仓库与现有调查任务不必推倒重来。
