## 首个可交接 Issue：RETAIL-00A 本地可运行基线

### 背景与用户目标

开发者需要在现有 OpenDot 基线建立真实可运行环境和明确的领域扩展入口，避免直接修改通用基础设施导致回归。当前仅有静态源码调查，未执行测试。

### 基线与现有实现

仓库、SHA 与证据见 RETAILOPS-BASELINE.md；启动前确认最新 HEAD 和工作区状态。CI 只有 workflow_dispatch；核对 Node 24、四个工程 lockfile、Makefile 与 CI 实际命令。

### 本次范围

- 安装原项目依赖，记录实际命令和运行环境。
- 跑现有类型检查、构建、单测、Durable、必要的 HTTP/E2E/Cloud 回归；区分真实依赖和 Fixture。
- 核对数据库迁移入口、产品 Runtime 启用、Goal/Handoff 入口、MCP 注册/审批/角色授权、前端路由、Trace 接入；输出文件路径和代码位置。
- 核对原仓库是否已有零售相关代码；列出扩展点、阻塞和风险。

### 明确不做

不开发零售业务，不重构原有 Runtime，不修改原有断言，不新增框架，不调用真实外部业务系统，不将凭证写进文档，不直接提交 main。

### 依赖与兼容边界

沿用当前锁文件、数据库、身份、权限和 API。若依赖安装或测试失败，先保留错误证据，提出独立修复 Issue，不擅自升级或删除测试。云端和真实模型不可用则标记未验证。

### 建议实现顺序

1. 环境、Git、依赖和配置核对。
2. 执行 BASELINE 文档中的命令，按 CI/Makefile 真实环境补齐前置条件。
3. 核对扩展入口与真实运行路径，记录所需开关。
4. 形成 `docs/retailops/local-baseline-receipt.md`（候选路径），包含命令、退出码、耗时、测试数、失败原因、环境类型、代码位置、未验证项。

### 验收与故障场景

类型检查/构建/原有测试有实际终端证据；能够辨别 Runtime 模式及审批类型；无真实凭证或 Docker/浏览器缺失时如实标注。不得以 mock 替换原有真实链路。失败需保留复现步骤，不声称通过。基线未通过时先处置 blocker，再进入领域实现。

### PR 切片和回滚

一个仅文档 PR；若需要修复环境或基线缺陷，另建 Issue/PR。记录原始工作区状态，不覆盖用户已有改动；文档 PR 可独立回滚。

### 完成说明

列出最终 HEAD、实际执行的测试命令/结果、PR（若用户授权）、未验证项及后续 Issue。当前状态：待认领、未执行。
