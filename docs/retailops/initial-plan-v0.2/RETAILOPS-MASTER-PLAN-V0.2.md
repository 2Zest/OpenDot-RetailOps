### 执行分类

- 串行主链：00C → 00D → 01 → 01P → 数据/仿真/草案等上游 → 04 → 06 → 08 → 09 → 10 → 11；12 可与 11 并行（相同执行合同冻结后）。03M 依赖 11 与 12，18C 依赖 03M，13B 依赖 18C 和 13A；发布必须等待 19、20、15。
- 首批独立调查/准备：00A-01、00F、00B-02、00B-03、00B-04H、00E-01、00E-02。使用独立 worktree；静态调查可以分给不同 subagent，真实运行只使用专用实例、端口和数据目录，资源冲突则串行。不要一次启动全部，主控建议先 00E-01、00B-02、00F 三项，确认资源后认领其余；所有真实探针需要对应授权。
- 合同冻结后可并行：02（数据）、03（仿真）、07（草案状态）；05P 只依赖领域契约可提前；05F 等待 02；00B-02V 与 00B-03V 分实例并行；00B-04V 必须等 Durable 验证。13A 可在 V0 验证期间做纯算法准备，13B 必须等闭环通过。19 与 20A/20 可并行，避免同时编辑共享接口。
- 独立不等于无验收；任何 subagent 只能负责分配的 Issue 或节点、不得自行创建额外依赖/分支策略/改变 PRD。主控负责审查共享入口、SQLite 迁移、路由、类型、权限配置，冲突路径指定单一所有者并串行合并。一个 Issue 原则上一个 PR，长任务按节点提交或拆 PR，未过节点不得合并为完成。

## 5. 节点级语义验收协议

1. N0 固定总体计划版本与哈希、PRD/ADR 版本、Issue/Plan、依赖证据及实际 HEAD；列允许文件和预期测试命令。任何尚未确认的候选文件/命令在认领时核实，未获主控确认不得实施。
2. 按 Plan 每次只执行一个节点，产出可复核 artifact；使用 `NODE-RECEIPT-TEMPLATE.md` 记录实际行为、实际文件、命令及结果、证据链接、未验证项。真实模型、自动化、fixture、静态、真实运行分别标记；模型自行声称完成不是证据。
3. 对照三层语义：总体目标/PRD（是否仍服务单店经营目标且无新增业务）、Issue/Plan（输入输出/职责/依赖/权限是否相符）、当前节点标准（可观察结果和测试是否满足）。每层逐项 PASS / DEVIATION / BLOCKED，说明原因，不能只比较关键字或文件存在。
4. 任一 DEVIATION：停止下游，写偏差 ID、影响范围、根因和修订方案，在原授权范围内修正并复测该节点及受影响上游/下游证据。迭代至三层 PASS 才执行下一节点；若不可行、需改变需求或权限，BLOCKED 并提交 ADR/变更请求，等待用户批准、更新计划版本与 DAG，再复核；不为了“通过”降低测试要求。
5. 节点全部 PASS 后检查 Issue 验收、测试、交付物和实际 diff；主控审查 PR，用户确认合并，记录合并 SHA 后 DONE。部分调查可以记录 BLOCKED 的能力，不将其当运行通过。既有 Issue #2 的 R01 补测需通过或用户明确同意延期并单独登记；不提前关闭。

## 6. 开发约束与证据规范

沿用 OpenDot TypeScript/Hono/SQLite/Zod/React/Pi SDK，未经 ADR 不引入第二套 Runtime、数据库或架构。主分支 main 保持原版，集成 develop/retailops，任务分支从最新集成 HEAD 创建，禁止强推/覆盖/删除用户工作区。功能 flags 仅在批准隔离实例配置；凭据不入 Git、不提交私人数据。所有写业务动作经过服务端鉴权、冻结草案、独立风控、人工审批、执行前复核、业务幂等与回执；通用 Product Approval 仅 create_private_artifact，不当作通用零售审批。原项目全量失败按基线对比，不篡改断言或用 mock 代替真实路径。PR 中明确静态/fixture/真实模型/真实 Runtime 的证据级别及未验证项。
