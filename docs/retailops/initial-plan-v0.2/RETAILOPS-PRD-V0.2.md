## 1. 产品目标与用户

RetailOps 的最终目标是形成一个面向 AI 应用开发与 Agent 应用开发岗位的高质量工程项目。单店商超不是要建设的传统零售管理系统，而是用来承载、检验 Agent 工程能力的受限业务场景：真实模型驱动的多步 Agent Loop、动态工具选择、可追溯上下文与证据、独立风控、业务审批、Durable 状态恢复和可证伪评测。V0 仍只覆盖一个生鲜 SKU、一个临期批次的仿真损耗治理闭环；本次调整不改变已批准的业务方向、DAG 或 V0/V1 边界。

主要角色：

- **店长/业务审批人**：确认业务目标、政策参数及决策草案；对业务动作作出明确批准或拒绝。
- **经营分析 Agent**：读取允许的数据并提出含依据和不确定性的草案；不得自行批准或执行。
- **独立风控角色**：按只读业务政策审查风险并给出结构化结果；与分析角色、审批人和执行服务分离。
- **受控仿真服务**：在确定性规则与批准范围内修改仿真状态，不连接真实 POS、支付、采购或供应商写端。
- **审计/评估人员**：复核输入快照、政策版本、审批、模拟执行与结果的关联。

## 2. 范围

### V0：单 SKU、单批次损耗治理

- 一家门店、一个待选 SKU、一个待选临期批次；具体商品、单位、保质期窗口和参数待业务审批。
- 以可追溯的公开历史观察和明确标记的仿真状态作为输入。公开数据不能伪装为目标门店的真实库存、批次、成本或实际销售件数。
- 形成只读分析结果和限界的决策草案；安全/质量硬规则优先于收益目标。
- 分析、独立风控、店长业务审批、受控仿真执行、状态核对与结果反馈形成可追溯闭环。
- 对重复请求、中断恢复、取消、权限拒绝和执行状态不确定建立明确合同；真实运行验收仍由对应下游 Runtime Issue 完成。

### V1：后续扩展，不属于 V0 承诺

在 V0 合同及运行验收完成后，才依据数据覆盖与用户决策扩展多 SKU、单店多批次、线上预占/完成/取消与线下销售共享库存、补货及多 SKU 经营异常诊断。20–50 SKU 是待验证的候选规模，不是已确定门槛。

## 3. 非目标与硬边界

- 不实现业务代码、数据库迁移、API、MCP 工具或 Agent 工具；这些属于下游 Issue。
- 不接真实 POS、支付、采购、称重硬件、供应商、商城或真实库存写接口。
- 不做竞品比价、叠券、大促、跨门店调拨、区域仓、消费者推荐、复杂物流或自动采购。
- 不允许 Agent 绕过业务审批、工具注册、Grant、权限策略或安全硬规则。
- 不因开源项目存在某种能力而声称 RetailOps 已具备该能力；不以静态调用链或 fixture 测试替代真实运行验收。

### 4.1 Agent Loop、进展判断与停止条件

经营分析 Agent 不是按固定步骤播放的 workflow。确定性服务可以负责授权、预算、持久化、硬规则、状态 guard 与执行门禁；“下一步查什么、证据是否充分、目标是否完成”必须由 Agent 根据当前观察和任务状态作出，并留下可复核的原因。

1. **接收任务**：读取目标、范围、当前批准的数据快照和策略版本；拒绝缺少授权或超出单店/单 SKU/单批次范围的任务。
2. **构造 Observation**：组合用户目标、权威业务事实引用及此前允许的只读工具结果；标明来源、时间、单位、覆盖范围和质量，不把摘要当原始事实。
3. **判断进展**：判断目标已满足、仍需信息、遇到冲突、证据过期或无法继续。对缺失事实明确列出缺口及其影响。
4. **动态选择动作**：若仍可安全推进，从本次已授权、已登记的工具集合中选择最小必要的只读查询/测算工具，或选择不调用工具并请求补充信息/拒绝；记录选择理由。不同情景仅在观察与证据需求足以解释时才应出现不同工具轨迹。
5. **观察工具结果并更新**：每次调用后核对调用结果、错误、时效与来源，再重新判断目标进展；不得把 timeout、空响应或未经验证的模型文本当作业务事实。
6. **停止或交付**：在目标完成、证据不足、遇到硬约束、授权失败、取消、超时或预算耗尽时停止。不得为了产生建议而绕过缺证据、错误或预算停止条件。

预算至少包含 Agent turn 数、工具调用数、LLM token、总耗时和安全重试次数；具体值由 D09/D16 及 RETAIL-06 N0 候选冻结，不在本文件中自行定默认值。只读调用仅允许在预算内按安全策略重试；授权失败不得换工具/Provider 绕过，任何有副作用调用不能由分析 Agent 重试。

结构化输出至少表达：目标/任务引用、结果类型（草案/需补证/拒绝/阻塞/失败）、结论或候选动作、证据引用及来源/时效、假设与不确定性、缺失证据、硬规则/风控状态、停止原因及关联 run/call 标识。具体字段 Schema 留给 RETAIL-07/后续接口任务确定。

### 4.2 Context、Working Memory 与历史经验

- **System Context**：稳定的角色指令、范围/安全政策摘要、工具授权边界和输出要求；不可被商家内容、检索文档或模型输出覆盖。
- **Task Context**：当前 Retail Task 的目标、店/SKU/批次范围、政策/数据快照版本、截止条件和批准状态；每次 Agent Run 绑定只读快照引用。
- **Working Memory**：本次运行中的 Observation、工具结果引用、已检查事项、证据缺口和短期推理进度；有大小/时效限制，不能充当权威账本。
- **历史经验**：带版本、来源、适用范围和时间戳的历史摘要或规则经验；只可作为检索线索，遇到冲突必须回到当前政策与库存等权威数据复核。Memory 不授予权限，不决定批准状态。
- **工具结果预算**：返回值先按字段白名单、长度和相关性裁剪；必要时生成摘要，但必须保留原始 Tool Call ID、内容摘要/hash、来源 URI/记录 ID、观测时间与裁剪标记。Token 超预算时删减低优先级历史上下文，不删安全政策、来源引用或当前约束。
- **经营知识检索**：已有场景将复杂 RAG/Memory/Context 优化列为后续可选项。本架构只允许在既有只读来源和授权工具内引用知识；不新增独立 RAG 系统、索引库、工具或 DAG 依赖。若检索超出已有 Issue，另提范围变更。

## 5. 数据解释合同

- **PUBLIC_HISTORICAL**：RETAIL-00E-02 研究的 FreshRetailNet 公开历史观察，许可证及样本证据见调查报告。已核实 `store_id=0` 的 74 个编码 `product_id` 在 97 天共同窗口有记录；该编码门店不等于可识别的真实商店，行数/覆盖也不等于真实业务覆盖。
- **DERIVED**：由有版本的公开/仿真输入按确定规则计算的特征、候选需求或统计量。保存派生方法版本与父输入引用。
- **SIMULATED**：以固定场景参数和种子生成的库存、批次、价格响应、订单、损耗或执行效果。必须醒目标记为模拟。
- **LIVE_DEVICE**：真实门店/POS/传感器设备数据层；当前没有相应接入证据，不得在数据模型、界面或报告中伪称已接入。

公开数据中的规范化销量/活动/折扣/缺货等字段不得转换成未观测到的件数、实际成本、真实售价、批次、现存库存、真实收入或毛利。缺货期间观察到的销量是受库存截断的观测，不能当作完整需求。价格响应属于仿真假设或待验证估计，不是因果结论。

## 6. 候选业务指标（公式待批准）

草案建议分别呈现模拟售出量、模拟报损量、剩余量、模拟收入/成本/毛利估计、折价幅度与规则命中情况；不得把互不等价的公开归一化数据与仿真金额相加。分母、成本来源、单位、舍入、折价弹性、无动作基准和时间窗均列入 `DECISIONS-PENDING.md`，在审批前不冻结公式，也不以 KPI 达标宣称产品有效。

## 7. 用户旅程与状态

1. 数据快照及模拟库存输入被校验并标注来源。
2. 分析角色生成不可执行的决策草案及证据引用。
3. 独立风控角色检查硬规则、数据质量、策略版本与草案摘要。
4. 店长查看完整证据并批准、拒绝或要求重新计算；参数/快照/政策改变会使旧审批失效。
5. 仿真服务核对摘要、权限、政策及库存前置条件后执行一次；冲突、超时或结果不确定时挂起并对账。
6. 审计记录最终状态；模拟反馈与历史观察分层呈现。

上述是需求状态语义，不表示现有 OpenDot Runtime 或 RetailOps 已实现本流程。

### Agent 风险、审批与可观测要求

- Agent 的语义审查可以指出政策解释冲突、证据不足、风险模式和不确定性；不能替代确定性校验。过期/质量禁售、授权、数量守恒、折扣上限、冻结摘要和状态转换必须由可测试的确定性边界判定。
- 分析 Agent 仅生成草案；独立风控 Agent 对同一 `draft_digest` 只读评估；业务审批必须绑定人类 actor 和不可变草案；执行服务仅在硬规则、授权、未撤销批准和最新快照均复核通过后运行仿真。
- 风控拒绝/错误/取消/超时不得流入业务审批；已批准草案若数据、政策、参数或摘要改变即失效。审批撤销发生在执行前须阻止执行。执行途中取消或超时若不能证明“未发生效果”，必须置为 `UNCERTAIN` 并对账；不得据重试推断失败或成功。
- Trace 从 Retail Task 贯通 Agent Run、每次 LLM Call、Tool Call、必要的 Handoff、Approval 和 Execution Receipt。每个节点保留 correlation/parent ID、时间、输入/输出摘要、模型/工具/策略版本、来源引用、token/耗时/结果状态；敏感凭据和不必要的原文不进入日志。

### RETAIL-06 与 RETAIL-19 的评测边界

RETAIL-06（GitHub Issue #27）原契约要求在两个不同场景中真实运行模型、依据观察动态选工具、呈现工具路径差异、缺证据时拒绝，并输出有来源草案；该两场景行为验收必须保留。当前 N4 只把其语义提升进架构，不运行模型或宣称通过。一般效果指标可记录任务成功/正确拒绝、工具选择正确率、轨迹差异合理性、证据覆盖、无依据结论、结构化输出有效性、失败处理、Token、延迟与成本，其具体目标值待批准或由对应下游 Issue 冻结。

以下为不可权衡的零容忍安全门槛：任何一次硬规则违规、未授权写入、审批绕过或重复业务副作用，均使安全验收失败并阻断任务；不得用成功率、业务收益、平均分或成本优势抵消，也不得通过调高阈值豁免。零次观测是必要条件，不单独构成通过证明。它们不是普通效果指标。

RETAIL-19（GitHub Issue #39）仍负责固定数据切分/随机种子/策略条件下的完整多场景经营对照实验、原始指标和负例报告；本 PRD 不把其实验套件或多策略结论挪给 RETAIL-06（GitHub Issue #27），也不缩减 RETAIL-06 的两个真实模型情景验收。
